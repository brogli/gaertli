# ADR-7: Diff UI with CodeMirror 6 merge

- `@codemirror/merge`: `MergeView` (side-by-side) and `unifiedMergeView` (unified), `collapseUnchanged`, chunk navigation, language highlighting, read-only.
- Go delivers old and new file content (`git show <rev>:<path>`, `cat-file --batch`); CodeMirror computes the visual diff.
- For hunk and line staging Go owns the truth: it re-diffs the path fresh, walks every fragment's own old/new line numbers, and applies a partial patch built from whichever lines the selection names. The UI sends the changed lines' own line numbers, not an index into either diff engine's hunk or chunk list — CodeMirror's chunks and git's own `-U3` hunks can group changes differently (git merges two changes within ~6 lines into one hunk; CodeMirror does not), so an ordinal from one would not reliably address the same change in the other. A per-hunk "Stage hunk" button sends every changed line of its own CodeMirror chunk; "Stage selected lines" sends the selected lines only. Either way the backend finds the change by line number, regardless of how many hunks or chunks it spans.
- Spike (M6): does `getChunks()` on a mounted `unifiedMergeView` map cleanly onto git's own hunk boundaries, closely enough to position the per-hunk button row? **Passed** against 4 fixtures (adjacent edits, pure insert, pure delete, edits at file start/end), each compared to that fixture's own `git diff -U0` (zero-context) hunk boundaries — the fair ground truth against CodeMirror's own un-padded chunks. Every fixture's git hunks mapped one-to-one, in order, onto `getChunks()`'s own chunks; the named fallback (git's own hunk boundaries sent from Go) was not built. Positioning the buttons never depended on git's `-U3` hunk boundaries matching CodeMirror's chunk boundaries — selection by line number closes that gap regardless of which fragment a line lands in.
