# Technical requirements (TR)

| ID | Requirement |
|---|---|
| TR-01 | Go ≥ 1.26. |
| TR-02 | Wails v3, exact version pinned (ADR-2). |
| TR-03 | Frontend: Vue 3.5 (Vapor mode not used), TypeScript strict, Vite, Pinia 4, VueUse, OpenVue 1.0. |
| TR-04 | System git ≥ 2.42 at runtime, checked on start. Older → clear error. |
| TR-05 | Windows: WebView2 runtime. |
| TR-06 | Linux: GTK4 + WebKitGTK 6.0 (the Wails v3 default). The GTK3 opt-in is not used. |
| TR-07 | No database. No network code in the app (the WSL core pipe is stdin/stdout). All core packages are pure Go: `CGO_ENABLED=0` must build `cmd/nebegit-core`. Only `internal/app` may depend on Wails and cgo. |
| TR-08 | Git output is parsed from machine formats only (`--porcelain`, `-z`, custom `--format`), never from human output. `--porcelain=v2` parsers ignore unknown header lines and record types. |
| TR-09 | Git runs with the user's environment plus `GIT_TERMINAL_PROMPT=0`; `GIT_OPTIONAL_LOCKS=0` on read-only calls, so polling never takes the index lock from the user's own commands; `GIT_EDITOR=true` where git would otherwise open an editor for a message (an operation's continue and skip, the squash and fixup rebase); `LC_MESSAGES=C` and `LANGUAGE=C` for English messages. Not `LC_ALL=C`: it would change the locale hooks and filters run in (QA-COMP-01). |
| TR-10 | Git is called with an argument list, never through a shell. Repo text never becomes an option: `--` before paths, `--end-of-options` before revisions (QA-SEC-03). |
| TR-11 | Every git call takes a `context.Context` and can be killed. |
| TR-12 | Child processes on Windows open no console window (`CREATE_NO_WINDOW`). The editor starts detached, so it outlives the app. |
| TR-13 | Settings live in one JSON file in the shell's OS user config dir (on Windows also for WSL repos). The shell pushes the relevant subset to each core on connect. Editor profiles are stored per environment (FR-ED-11). |
| TR-14 | Tests use real git against temp repos; a local bare repo is the remote. Tests keep git away from the user's own config. Dependency download is a separate setup step; the test run needs no network, and CI runs it offline to prove that (QA-MNT-03). |
| TR-15 | A feature spec is written only after the research it depends on exists in the plans dir `research/`. |
| TR-16 | Research uses primary sources: official docs, release notes, source code. Each finding has a link and a date. |
| TR-17 | For every non-trivial problem, look for an established library or proven pattern first. Own code only if nothing fits; the spec states why (ADR-8). |
| TR-18 | Preference order. Go: standard library → `golang.org/x/*` → established third-party → own code. Frontend: Vue core → VueUse → OpenVue / established lib → own code. |
| TR-19 | "Established": release or commits in the last 12 months, widely used, permissive licence (MIT, BSD, Apache-2.0, MPL-2.0; for fonts also OFL-1.1), acceptable transitive dependencies, works on Windows and Linux. The licence rule applies to everything linked into the app or its compiled test binaries; standalone dev tools that are only run (linters, CI actions, JS dev tooling such as the test runner) are exempt. |
| TR-20 | Every added dependency is listed in `dependencies.md`: purpose, alternatives, why chosen, licence, date checked. |
| TR-22 | Supported targets: `windows/amd64`, `linux/amd64`. Best effort: `darwin/arm64`, built in CI, untested (QA-PORT-04). No macOS-specific code beyond what Wails needs. |
| TR-23 | pnpm is the only JS package manager; npm is used for nothing, installs and queries alike. `pnpm-lock.yaml` is committed; `package-lock.json` must not exist (CI check). pnpm and Node come from the Nix shell, and `flake.lock` is their only version pin: `package.json` has no `packageManager` or `engines` field. Where there is no Nix (Windows and macOS runners, native Windows development) the same majors come from their official setup. CI installs with `--frozen-lockfile`. The Taskfile's frontend tasks call pnpm. |
| TR-24 | Everything non-Go comes from a Nix dev shell + direnv: `flake.nix`, committed `flake.lock` (nixpkgs from nixos-unstable), `.envrc` with `use flake`. The shell supplies Node.js 24, pnpm 11, `golangci-lint`, `treefmt`, `nixfmt`, and on Linux GTK4, WebKitGTK 6.0, pkg-config and gcc. gcc comes from Nix so cgo links against the same glibc as the Nix libraries; binaries built in this shell run only inside it. |
| TR-25 | Go is not supplied by Nix. The `go` and `toolchain` lines in `go.mod` fix the version. `wails3` and `task` are `tool` directives in `go.mod`, run with `go tool <name>`. `golangci-lint` is not: its docs advise against `go tool`; it comes from the Nix shell and from its official CI action. |
| TR-26 | The Nix shell serves development and CI's Linux check jobs (lint, tests, e2e), so those run with the same tools as a local checkout. Release binaries are built on stock runners, since binaries built in the shell run only inside it; Windows and macOS jobs use the official setup actions. |
| TR-27 | Native Windows development is not covered by Nix. Documented manual path: Node 24 + pnpm by hand, `golangci-lint` binary, the rest via `go tool`. Recommended: develop inside WSL with the Nix shell and cross-compile the Windows shell from there (it needs no cgo). The Linux build under WSLg is a development convenience, not a supported way to use WSL repos (QA-PORT-02). |
| TR-28 | The core API is one Go interface in `internal/core`, using only JSON-serialisable types. Two implementations: `internal/services` (in-process, local repos) and a generated JSON-RPC client (WSL repos). `tools/gencore` generates from the interface: the RPC client, the RPC dispatcher for `nebegit-core`, and the facade struct the shell binds to Wails, which forwards each call to the core its worktree id or repo path names (ADR-3), not the window making the call. A method is written once. The shell never runs git itself. |
| TR-29 | Test-driven. For every acceptance case: failing test first, least code that passes, refactor. No production code without a failing test that asks for it. |
| TR-30 | Traceability. Test names carry the requirement ID: Go `TestFR_LOG_01_ListsAllBranches`, Vitest `it('FR-LOG-01 lists all branches')`. `tools/trace` requires every MUST `FR-*` id and every `QA-*` id from the requirements, and fails CI if one appears in none of: a test name, the manual checklist (`testing.md`), `tools/trace/pending.txt` (an allow-list for tests still owed). |
| TR-31 | Frontend tests: component tests (Vitest + Vue Test Utils, mocked bindings) by default. Playwright against the Vite dev server with a mocked Go layer only where a component test cannot prove the case (virtual scrolling, cross-view keyboard flow). Playwright against the app in Wails server mode, with the real core and git on scratch repos, for flows through UI, core and git that mocks cannot prove: an outside change reaching the UI, a UI action's effect on the repo. The spec states why. Native windows are tested by hand (`testing.md`). |
| TR-32 | Process. `docs/` holds only the requirements and architecture files listed in `docs/requirements.md` and `docs/architecture.md`, kept current. Specs, research notes, roadmap, and status live in a plans directory outside the repo; its location is in the untracked `CLAUDE.local.md`. Work happens on branches off `main` (`dev`, later feature branches); the owner merges them into `main`, which also receives Renovate's dependency updates (TR-41). A working branch takes in `main` by merging it; sessions never commit to `main`. Specs are self-approved after the template checklist. Critical decisions go to the owner: failed spike, ADR/TR/MUST change, dependency failing TR-19, release, anything destructive. |
| TR-33 | The frontend follows what the official scaffold `npm create vue@latest` generates for TypeScript + Pinia + Vitest + Playwright: `<script setup lang="ts">` Composition API, Pinia setup stores, the `tsconfig.app.json`/`tsconfig.node.json`/`tsconfig.vitest.json` split with `vue-tsc --build`, ESLint flat config with oxlint (`eslint-plugin-oxlint`, `.oxlintrc.json`) and `eslint-config-prettier`, which leaves formatting to the formatter; oxfmt as the formatter (create-vue's experimental choice, taken on purpose); unit and component tests in `__tests__` folders next to the code they test, named `*.spec.ts`; the `@` alias for imports from `src/`; scripts named as the scaffold names them. Project-specific `src/` folders (`composables/`, `lib/`, `locales/`, `menus/`, `testing/`, `views/`) are allowed. Divergences are tracked in the plans directory and closed by a spec. |
| TR-34 | Icons: OpenIcons, OpenVue's continuation of PrimeIcons, for every icon the app draws itself; OpenVue's components keep their built-in icons. No Unicode glyphs, emoji or own SVGs as icons. |
| TR-35 | UI texts (FR-UX-11): vue-i18n in Composition API mode with one message file per language; English is the source. Components and stores hold no display text. |
| TR-36 | Notices use OpenVue's Toast as it comes: its severities (error, warning, info, success) with their standard look, in its default position, top right. The app's extras (git's output behind "show details", copy, actions) sit inside the standard message. |
| TR-37 | The UI uses OpenVue's Aura theme. Every control is an OpenVue component. A change to how OpenVue looks is a design-token override in one project preset over Aura, never CSS. The app's own styles lay out its views and draw only what OpenVue has no component for (graph, comparison marks); they never restyle OpenVue components or native controls. |
| TR-38 | `treefmt` is the one command that checks and formats the whole repo. It first runs the linters with their fixes (TR-39), then the formatters: oxfmt for TypeScript, Vue, CSS and Markdown, gofmt and goimports for Go, nixfmt for Nix. The pipeline runs `treefmt --ci`, which fails on any lint error or unformatted file. JS tools run through pnpm, so their versions come from the lockfile; the rest come from the Nix shell. |
| TR-39 | Linters: golangci-lint for Go; oxlint, then ESLint, for TypeScript and Vue, with Playwright rules for e2e specs and Vitest rules for unit tests; stylelint (standard, standard-vue, Tailwind) for CSS and `<style>` blocks. An `.editorconfig` gives every editor the same basics: encoding, indentation, final newline, LF. |
| TR-40 | TypeScript is typed throughout: no `any`; no non-null assertion or `as` cast without a comment saying why; exported functions, composables and store actions declare their parameter and return types; components use the type-based `defineProps<>()` and `defineEmits<>()`; outside data (parsed JSON, local storage) is `unknown` until narrowed. typescript-eslint enforces every part it has a rule for. |
| TR-41 | Every dependency is pinned to an exact version: npm packages exactly, GitHub Actions by commit hash with the version as a comment. Renovate keeps them current against `main`: minor, patch, pin and digest updates of dependencies at 1.0 or later, and lockfile maintenance, merge automatically once CI passes; majors and every 0.x update wait for review. No release younger than 7 days is taken, which pnpm enforces at resolution too. Go modules, GitHub Actions and the Nix inputs are covered as well. Wails' Go module and `@wailsio/runtime` update together, in one change and never automatically (TR-02). |
| TR-42 | CI jobs run with read-only token permissions and a time limit, cache what they download (pnpm store, Go modules), and a failing e2e job uploads its report. |
| TR-43 | Styling: Tailwind CSS v4 (its Vite plugin, configured in CSS) is the styling layer; views and components style with utility classes. A `<style>` block holds only what utilities cannot express (keyframes, third-party DOM such as CodeMirror's). OpenVue's theme tokens reach Tailwind through `tailwindcss-primeui`; CSS layers order theme, base, OpenVue, components, utilities; Tailwind's dark variant follows the app's own dark class (TR-37). |
